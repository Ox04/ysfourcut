# 03 — 정확한 흑백·용지 PNG
상태: done (WSL의 실제 Linux .NET + Skia에서 PNG 생성과 픽셀 일치를 확인)
실행 환경: WSL Fedora Linux 42, .NET SDK 10.0.400, SkiaSharp 3.119.4 네이티브 linux-x64
사용 모델/effort: Opus 5 / high (사용자가 Claude Code에서 선택한 값)

## 바뀐 것
- 패키지: `CrossEscPos.Rendering.Skia` **1.2.0**(전이: `CrossEscPos.Abstractions` 1.2.0, `SkiaSharp` 3.119.4 + Linux/Win32/macOS 네이티브 자산) 복원. `RestorePackagesWithLockFile`로 `apps/print-host/packages.lock.json` 생성. 취약 패키지 없음(`dotnet list package --vulnerable --include-transitive`).
- `Rendering/MonoBitmapDecoder.cs` — msb-first / 1=검정 / 위에서 아래로 해제. x=0이 0x80, x=7이 0x01. 행 우측 패딩 비트는 읽지 않는다.
- `Rendering/ReceiptLayout.cs` — 정수 dot 배치. `paperHeight = leading + contentHeight + trailing`, 내용 원점 `(sideMarginDots, leadingFeedDots)`, mm/DPI는 파생 계산. 인쇄 가능 폭 초과·0 이하·이송 불일치는 예외.
- `Rendering/CrossEscPosSkiaAdapter.cs` — `IReceiptImageBackend`(얇은 어댑터). `SkiaImageFactory.FromPixels/Create/CreateCanvas`와 `SkiaImageEncoder.EncodePng`만 사용. Core의 `PaperConfiguration`·`Receipt`·`ReceiptBitmapLine`·`FeedEscPos`·파일 로거는 호출하지 않는다.
- `Rendering/ReceiptPaperComposer.cs` — 순백 캔버스 + 정수 (x,y) 1:1 그리기. 확대/축소 overload 미사용.
- `Rendering/ReceiptRenderer.cs` — decode → content PNG → paper PNG. 인코딩 **전** 픽셀 수 검사, **후** PNG IHDR로 실제 크기 재검사, 작업 합계 바이트 검사. 이미지/캔버스는 `using`으로 dispose.
- `Rendering/RenderLimits.cs` — 이미지당 8,000,000픽셀 / 작업당 32MiB, `RenderLimitExceededException`, PNG 헤더 판독기.
- `Rendering/IReceiptAppearanceRenderer.cs` — 04번 구현 지점(요청에 layout·paper 이미지·cutStyle·revision·seed·효과 목록). 기본은 `UnimplementedAppearanceRenderer`로 **미구현을 명시**하고 가짜 이미지를 만들지 않는다.
- 오류 코드 `RENDER_LIMIT_EXCEEDED`를 C#(`ErrorCodes`)과 TS(`contract.ts` + 한국어 안내) 양쪽에 추가.
- `Program.cs`에 렌더링 서비스 DI 등록(HTTP 경로는 추가하지 않음). 호스트 버전 0.3.0.
- `tests/print-host/ReceiptRenderingTests.cs`(12개), `RenderInspectionTool.cs`(환경 변수로만 동작하는 개발 확인용), `THIRD_PARTY_NOTICES.md` 신설, `docs/API_CONTRACT.md`에 렌더링 절 추가.

## 다음 작업이 알아야 할 계약
- 진입점: `ReceiptRenderer.Render(DecodedBitmap, PrinterProfile, appearanceSeed)` → `ReceiptRenderResult(Layout, Content, Paper, Appearance?, AppearanceUnavailableReason, SourceDigest)`. `DecodedBitmap`은 02번 검증기가 만드는 그 타입이며 `SourceDigest`도 그대로 전달된다.
- `RenderedPng(Kind, Bytes, WidthPx, HeightPx)`의 Kind는 `content`/`paper`/`appearance`(`ArtifactKinds`).
- **04번**: `IReceiptAppearanceRenderer`를 구현하고 DI 등록만 바꾸면 `ReceiptRenderer`가 지면 이미지가 살아 있는 동안 호출한다. `request.Paper`는 호출 동안에만 유효하고 수정하면 안 된다. appearance 픽셀 한도도 렌더러가 검사한다.
- **05번**: 작업 큐·상태·잠금·artifact 보관·HTTP는 아직 없다. 렌더러는 이미지 바이트만 만들고 디스크에 쓰지 않는다. `RenderLimitExceededException.Code/Details`를 그대로 구조화 오류로 내보내면 된다.
- 좁은 내용의 배치 규칙: 인쇄 가능 폭보다 좁으면 **왼쪽 정렬**(원점 `(32,24)`). 가운데 정렬이 필요하면 제품 결정으로 별도 처리한다.

## 검증
- `npm run test:host` **78개 통과**(기존 65 + 렌더링 12 + 확인 도구 1). `npm run typecheck` / `lint` / `test`(웹 8개) 통과.
- 픽셀 일치: content PNG를 `SKBitmap.Decode`로 다시 읽어 입력 비트와 전 픽셀 비교. 고정 패턴에 0x80(x=0)·0x01(x=7)·마지막 열(x=8)·마지막 행·홀수 폭(9)·8의 배수 폭(16)·비정렬 폭(100)을 포함.
- 지면: `paper`의 contentRect crop이 content와 픽셀 단위로 동일하고, 내용 영역 밖은 전부 순백(여백·이송 중복 없음)임을 전 픽셀 확인.
- 치수: 576×1788 입력 → paper **640×1876**, 80×234.5mm, 원점 (32,24), 203.2DPI. 58mm는 464 폭·원점 (40,24).
- PNG 압축 바이트 동일성은 요구하지 않고 디코딩 픽셀/치수를 비교했다. 같은 입력 두 번 렌더 시 픽셀이 동일함도 확인.
- 한도: 픽셀 한도 초과 시 렌더 전에 `RENDER_LIMIT_EXCEEDED`(limit=pixelsPerImage), 인코딩 합계 초과 시 limit=encodedBytesPerJob.
- Linux Skia 네이티브 로드: 실제로 `SkiaImageFactory.FromPixels` → Bgra8888/Opaque, `EncodePng` 정상 PNG, 캔버스 1:1 그리기 픽셀 일치를 별도 스크래치 실행으로 먼저 확인한 뒤 본 구현에 반영했다. fontconfig/freetype 외 추가 OS 패키지 설치는 필요 없었다.
- 눈으로 확인: `YSFOURCUT_RENDER_INSPECT_DIR=<경로> dotnet test --filter RenderInspectionTool`로 인공 패턴 PNG를 만들어 확인했다(스크래치 폴더, 저장소 밖). 640×568 지면에 576×480 내용이 (32,24)에 놓이고 1픽셀 격자/세로선이 보간 없이 선명함을 확인. **인공 패턴 개발 확인용이며 앱 실행 경로는 결과를 디스크에 쓰지 않는다.**
- 호스트 재기동 확인: `npm run dev`로 새 빌드 실행, `hostVersion=0.3.0`, health 200. 렌더링 DI 등록이 기동을 막지 않는다.
