# 05 — 웹 요청부터 서버 PNG 조회까지
상태: partial (WSL에서 API·worker·보관·정리 전부 실제 확인. 개발 확인 화면의 브라우저 동작만 사용자 확인 필요)
실행 환경: WSL Fedora Linux 42, .NET SDK 10.0.400, Node 24.19.0. 호스트 버전 0.5.0
사용 모델/effort: Opus 5 / high (사용자가 Claude Code에서 선택한 값)

## 바뀐 것
- `Printing/IPrinterBackend.cs` — 공통 백엔드 경계. `Printing/Virtual/VirtualReceiptPrinter.cs`가 유일한 등록 구현이며 Windows 어댑터는 등록하지 않는다.
- `Worker/RenderWorkerProtocol.cs`, `Worker/RenderWorkerEntryPoint.cs` — `--print-worker`로 시작하는 **별도 렌더 프로세스**. 익명 파이프 2개(요청/응답)로 `[4바이트 길이][JSON 머리말][원시 바이트]` 프레임을 주고받는다. 표준 출력에 이미지·base64를 쓰지 않는다. 부모 PID를 감시해 호스트가 사라지면 스스로 종료한다.
- `Program.cs` 첫머리에서 worker 호출을 분기한다(웹 호스트를 만들지 않음). 실행 파일은 apphost면 자기 자신, 아니면 `dotnet <host.dll>`로 결정하고 인수는 `ArgumentList`로만 전달한다(.exe/cmd.exe 고정 없음).
- `Jobs/PrintJob.cs`(상태·스냅샷·digest·seed), `Jobs/PrintJobManager.cs`(전역 1작업 잠금, UUID+내용 중복 흡수, 상태 전이, 종료 정리), `Jobs/PrintJobRecordStore.cs`(사진 없는 기록, 임시 파일+rename), `Jobs/JobMaintenanceService.cs`(시작 정리 + 30초 TTL 청소 + 종료 시 worker 정리).
- `Artifacts/InMemoryReceiptArtifactStore.cs` — 세션에 묶인 메모리 PNG 캐시. TTL 10분(조회로 연장 없음), 세션 3작업/64MiB, 호스트 128MiB, 작업 32MiB.
- `Api/PrintJobEndpoints.cs` 재작성 — 접수 202, 상태 조회, artifact 조회(no-store), 세션 정리. `resolve`/`fault`만 501(06번).
- 오류 코드 추가(C#/TS 양쪽): `RENDER_TIMEOUT`, `VIRTUAL_RENDER_FAILED`, `JOB_RECORD_FAILED`, `HOST_RESTARTED`. 계약에 `failure`, `ClearArtifactsResponse` 추가.
- `packages/imaging`에 실제 함수 추가(`packMonoBitmap`, `strideBytesFor`, `toBase64`) + 테스트 5개. `apps/web`이 이 패키지를 의존한다.
- `apps/web/src/dev/DevPrintCheck.tsx` — 인공 비트맵 제출 → 상태 폴링 → 인증 fetch로 Blob PNG 표시 → 세션 정리. **제품 UI가 아니다**(07번).
- `docs/API_CONTRACT.md`에 접수/상태/보관/기록 절 추가.

## 다음 작업이 알아야 할 계약
- **worker 실행 위치**: `apps/print-host` 자신이다. `dotnet apps/print-host/bin/.../YsFourcut.Host.dll --print-worker --request-pipe <handle> --response-pipe <handle> --parent-pid <pid>`로 뜬다. 별도 프로젝트가 아니다.
- 진행 중 작업은 서비스 전체에서 하나. 같은 UUID+같은 내용은 기존 작업을 그대로 반환(재렌더 없음), 다른 내용은 409 `JOB_ID_CONFLICT`, 다른 작업 진행 중이면 409 `PRINTER_BUSY`.
- artifact 응답 규칙: 진행 중 409 `ARTIFACT_NOT_READY`, 만료·정리·재시작 410 `ARTIFACT_EXPIRED`, 없는 작업/다른 세션/결과 없는 실패 404 `ARTIFACT_NOT_FOUND`.
- 작업 기록은 `~/.local/state/YSFourcut/jobs/<uuid>.json`. 기록 실패 시 출력을 시작하지 않는다(`JOB_RECORD_FAILED`). 재시작 시 미완료 기록은 `virtual_failed` + `HOST_RESTARTED`로 정리하고 자동 재렌더링하지 않는다.
- **06번**: 오류 주입(`PUT /api/virtual-printer/fault`)과 `resolve`가 남았다. 지연은 렌더 시작 전에 적용하고 10초 예산에서 제외해야 한다(`VirtualPrinterOptions.RenderTimeout`). 실패 주입은 `PrintJobManager.RenderAsync` 앞이 자연스러운 지점이다.
- 테스트에서 진행 중 상태를 만들려면 `PrintHostFactory { BackendOverride = new BlockingPrinterBackend() }`를 쓴다. `StateDirectory`/`KeepStateDirectory`로 기록 폴더도 지정할 수 있다.

## 검증
- `npm run test:all`: .NET **109개**(3회 연속 통과), 웹 13개(imaging 5 + web 8). typecheck/lint/build 통과.
- worker 경로: 실제 자식 프로세스가 뜨고 파이프로 세 PNG를 받는 것을 확인. **worker 결과가 in-process 렌더 결과와 바이트 단위로 동일**함도 확인. 10초 예산 초과 시 `RENDER_TIMEOUT`으로 worker 정리, worker의 한도 초과는 `RENDER_LIMIT_EXCEEDED`로 전달.
- 흐름 테스트: 접수 202 → 상태 폴링 → 세 PNG 조회(200, `image/png`, `no-store`, 디코딩 크기 일치). 같은 UUID+같은 내용 재요청 시 `createdAtUtc`와 **artifact 만료 시각이 그대로**여서 다시 렌더링하지 않았음을 확인. 같은 UUID+다른 내용은 409.
- 경합/수명: 진행 중 두 번째 접수 409 `PRINTER_BUSY`(백엔드 호출 1회), 진행 중 artifact 409, 진행 중 정리 409, 실패 작업은 `failure.code`와 available=false, TTL 10분 경과 후 410, 세션 정리 후 410, 다른 세션은 404.
- 기록: 실제 파일을 열어 `clientJobId/requestDigest/profileId/revision/mode/state/시각`만 있고 사진·base64가 없음을 확인. 재시작 정리 테스트에서 이전 실행의 `rendering` 기록이 `virtual_failed`+`HOST_RESTARTED`가 되고 **백엔드 호출이 0회**임을 확인.
- 실서버(WSL, Vite 프록시 경유) curl 확인: 접수 → `state=rendered`, `isPhysical=false`, `spoolJobId=null`, layout 640×288/원점(32,24), `simulation.isSimulated=true`, 세 PNG 200 + 실제 크기(576×200 / 640×288 / 688×336).
- 종료: `npm run dev`에 SIGINT → 호스트와 worker 프로세스 모두 사라짐(`ps`로 확인). 서버가 꺼진 상태의 접수는 연결 실패로 끝나고 성공하지 않는다.
- 서버 로그에 이미지·base64 흔적 0건.
- **미실행**: 개발 확인 화면을 Windows 브라우저에서 눌러 PNG가 화면에 뜨는지. HTTP 단계는 curl로 모두 확인했지만 Blob 표시와 폴링 동작은 사용자 확인이 필요하다. dev 서버는 새 빌드(0.5.0)로 실행 상태로 두었다.
- **관찰한 불안정 1건**: 전체 스위트 첫 실행에서 `PrinterProfileApiTests.Saves_selected_profile_and_keeps_it_after_reload`가 한 번 실패했다(원인 미확인, 메시지 미수집). 이후 단독 실행과 전체 3회 연속 실행에서 재현되지 않았다. 06번에서 다시 보이면 원인을 확인해야 한다.
