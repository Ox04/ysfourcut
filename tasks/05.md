# 05 — 웹 요청부터 서버 PNG 조회까지

- 권장 모델: **Opus 5 / high**
- 입력: `05 진행해`
- 선행 작업: 02, 03, 04.
- 목표: 하나의 실제 출력 작업이 공통 API를 통해 접수되고 서버 PNG로 조회됨.

## 이번에 읽을 것

- 진행표, 02/04 handoff, 실제 API 타입/인증과 렌더 인터페이스.
- `SERVICE_DESIGN.md`의 8~10절 중 공통/virtual 항목.
- `VIRTUAL_PRINTER_DESIGN.md`의 3절·6~9절, `WSL_DEVELOPMENT.md`의 5절.

## 할 일

1. `IPrinterBackend`와 `VirtualReceiptPrinter`를 연결한다. 서버 모드만 사용하며 Windows 어댑터를 호출하지 않는다.
2. `POST /api/print-jobs`가 UUID/내용 digest로 중복을 막고 202를 반환하게 한다. 같은 ID/같은 내용은 기존 작업, 다른 내용은 409다. 서비스 전체의 원자적 진행 작업 잠금을 둔다.
3. Linux에서도 실행되는 별도 렌더 worker를 사용한다. host/job ID가 있는 제한된 메시지와 파이프로 요청/PNG를 전달하고 stdout에 이미지 로그를 쓰지 않는다.
4. accepted → rendering → rendered/virtual_failed, 프로필·모드·외관 revision 스냅샷, layout/실물 여부/spool ID 없는 응답을 제공한다. 세 필수 PNG를 모두 받은 뒤 한 번에 게시한다.
5. 인증 세션에 묶인 메모리 artifact store와 조회/정리 API를 구현한다. 처음부터 TTL 10분, 세션당 3건/64MiB, 호스트 128MiB, 작업당 PNG 32MiB를 적용한다. 공개 결과 파일 경로를 만들지 않는다.
6. 사진 없는 작업 기록을 원자적으로 저장한다. 기록 실패 시 실행하지 않으며, 앱 시작 시 미완료 virtual 기록을 실패로 정리하고 자동 재렌더링하지 않는다.
7. 최소 개발 확인 화면에서 인공 비트맵 제출 → 상태 조회 → 인증 fetch/Blob PNG 표시까지 연결한다. 이 화면은 제품 UI 디자인이 아니다.

## 완료 확인

- 실제 .NET API를 거쳐 세 PNG를 받는다. 서버가 꺼지면 성공하지 않는다.
- 동일 UUID 두 번 요청해도 worker/이미지 작업이 한 개만 생긴다.
- 다른 세션 조회 거부, no-store, 없는 작업 404, 진행 중 409, 만료 410 확인.
- 기본 타임아웃/부모 종료에서 worker와 잠금을 정리한다. 상세 오류 주입·경합 검수는 06에서 확장한다.

## 이번에 하지 않을 것

카메라, 제품 UI 재디자인, 오류 주입 패널, 실제 인쇄. 05 handoff에 실제 endpoint와 worker 실행 위치를 남기고 멈춘다.
